# MCP Authorization

<!-- verified: 2026-08-12 · current spec revision: 2026-07-28 -->

> How a remote MCP server establishes who is calling and what they may do — OAuth 2.1 with issuer validation and Client ID Metadata Documents, and the scoping discipline that makes prompt injection survivable.

**Tier:** advanced
**Use when:** the server is remote, multi-user, or handles anything a user would not want another user to see.
**Avoid when:** stdio-only, single-user, running as that user. The process boundary is the authorization boundary and adding OAuth buys nothing.
**Cost profile:** a day or two with a good library; considerably more without one. Getting it wrong is a data-breach class of bug.

---

## 1. Problem it solves

A remote MCP server receives requests generated by a language model that has read attacker-influenceable content — web pages, emails, documents, other tools' output. Two distinct questions follow:

1. **Who is this?** Authentication. Solved by OAuth, which the spec builds on.
2. **What may they reach?** Authorization. Solved by scoping, and **the scope must never come from anything the model produced.**

The second is where servers go wrong. A tool signature like `get_records(tenant_id: str)` looks reasonable and is a data-leak waiting for one injected instruction. The model is not a trust boundary.

The 2026-07-28 revision tightened the OAuth surface specifically: RFC 9207 issuer validation is required, Dynamic Client Registration is deprecated in favour of Client ID Metadata Documents (CIMD), client credentials are bound to their minting issuer, and clients declare `application_type` so desktop and CLI apps can use localhost redirects.

## 3. Components

| Component | Responsibility | Notes | Primary failure mode |
|---|---|---|---|
| Protected resource metadata | Tells clients which AS to use | Served by the MCP server | Missing → clients cannot discover the AS |
| Authorization server | Issues tokens; owns consent | Your IdP, or a dedicated AS | Tokens without an audience claim |
| Client identity | Identifies the calling app | **CIMD** (DCR deprecated) | Still using Dynamic Client Registration |
| Issuer validation | Client validates `iss` before redeeming a code | RFC 9207, now required | Skipped → mix-up attacks |
| PKCE | Binds the code to the client | Required | Omitted on public clients |
| `application_type` | Native vs web client | Enables localhost redirects for desktop/CLI | Unset → desktop flows blocked |
| Token validator | Signature, audience, expiry, scopes | Server-side, per request | Audience unchecked → token replay across services |
| Scope deriver | Token → tenant/user/permissions | **The security boundary** | Deriving from tool arguments |
| Rate limiter | Per-principal quotas | Outside the model's reach | Absent → one loop exhausts a quota |
| Audit log | Principal, tool, args, outcome | Append-only | Logs the call but not the principal |

## 4. Data flow

1. Client calls without a valid token → server returns `401` with `WWW-Authenticate` pointing at its protected-resource metadata.
2. Client fetches that metadata, learns the authorization server.
3. Client starts an OAuth flow with PKCE, identifying itself via CIMD, declaring `application_type`.
4. User consents. Authorization server redirects with a code and an `iss` parameter.
5. **Client validates `iss` against the expected issuer before redeeming the code.** Skipping this is the mix-up attack.
6. Client redeems the code for an access token whose **audience is this MCP server**.
7. Every subsequent request carries the token. Server validates signature, audience, expiry, and scopes.
8. Server derives tenant/user/permissions from the token claims. Tool arguments are treated as untrusted data throughout.
9. Rate limits are applied per principal. Every call is audited with its principal.

## 5. Contracts

```python
from pydantic import BaseModel, Field
from typing import Literal

class Principal(BaseModel):
    """Derived from the token. The ONLY source of identity in the server."""
    subject: str
    tenant_id: str
    scopes: set[str]
    application: str = Field(description="Calling app, from CIMD client id")
    expires_at: float

class ToolScope(BaseModel):
    tool: str
    required_scopes: set[str]
    reversibility: Literal["free", "cheap", "expensive", "impossible"]
    rate_limit_per_hour: int | None = None

# Declared per tool, checked before dispatch, never negotiable by the model.
TOOL_SCOPES = {
    "search_orders":       ToolScope(tool="search_orders", required_scopes={"orders:read"},
                                     reversibility="free"),
    "update_order_status": ToolScope(tool="update_order_status", required_scopes={"orders:write"},
                                     reversibility="cheap", rate_limit_per_hour=100),
    "issue_refund":        ToolScope(tool="issue_refund",
                                     required_scopes={"orders:write", "payments:refund"},
                                     reversibility="expensive", rate_limit_per_hour=10),
}
```

## 6. Reference implementation

```python
import jwt, time
from fastapi import Request, HTTPException

EXPECTED_ISSUER = "https://auth.example.com"
THIS_SERVER_AUDIENCE = "https://mcp.example.com"

def authenticate(request: Request) -> Principal:
    header = request.headers.get("Authorization", "")
    if not header.startswith("Bearer "):
        raise HTTPException(401, headers={
            "WWW-Authenticate":
                'Bearer resource_metadata="https://mcp.example.com/.well-known'
                '/oauth-protected-resource"'})

    try:
        claims = jwt.decode(
            header[7:], key=jwks_client.get_signing_key_from_jwt(header[7:]).key,
            algorithms=["RS256"],
            audience=THIS_SERVER_AUDIENCE,     # token replay across services fails here
            issuer=EXPECTED_ISSUER)
    except jwt.PyJWTError as e:
        raise HTTPException(401, f"Invalid token: {e}")

    return Principal(subject=claims["sub"], tenant_id=claims["tenant_id"],
                     scopes=set(claims.get("scope", "").split()),
                     application=claims.get("client_id", "unknown"),
                     expires_at=claims["exp"])

def authorize(principal: Principal, tool_name: str) -> None:
    spec = TOOL_SCOPES.get(tool_name)
    if spec is None:
        raise HTTPException(403, "Unknown tool")          # fail closed
    missing = spec.required_scopes - principal.scopes
    if missing:
        # Actionable for the model: it should stop, not retry.
        raise ToolError(f"Missing permission: {', '.join(sorted(missing))}. "
                        f"Ask the user to grant it. Do not retry.")
    if spec.rate_limit_per_hour and \
       limiter.count(principal.subject, tool_name) >= spec.rate_limit_per_hour:
        raise ToolError(f"Rate limit reached for {tool_name}. Wait before retrying.")

@mcp.tool()
def search_orders(ctx, customer_email: str | None = None, status: str | None = None) -> str:
    """Search orders. Scope comes from the token, never from arguments."""
    principal = authenticate(ctx.request)
    authorize(principal, "search_orders")
    audit.log(principal=principal.subject, tenant=principal.tenant_id,
              tool="search_orders", args={"customer_email": customer_email, "status": status})
    # tenant_id from the PRINCIPAL. There is deliberately no tenant argument on this tool.
    rows, total = repo.search(tenant_id=principal.tenant_id,
                              email=customer_email, status=status)
    return format_orders(rows, total)
```

Client-side issuer validation — the step most implementations skip:

```python
def redeem_code(code: str, iss_from_redirect: str, verifier: str) -> str:
    # RFC 9207: validate BEFORE redeeming. Without this, an attacker-controlled AS
    # can have your client redeem a code at the wrong issuer.
    if iss_from_redirect != EXPECTED_ISSUER:
        raise SecurityError(f"Issuer mismatch: {iss_from_redirect!r} != {EXPECTED_ISSUER!r}")
    return token_endpoint_post(code=code, code_verifier=verifier)
```

## 7. Configuration knobs

| Knob | Default | Effect | Change it when |
|---|---|---|---|
| Token lifetime | 1 h | Exposure window | Shorter for high-privilege scopes |
| Refresh tokens | rotating | Replay resistance | Always rotate |
| Scope granularity | per resource + action | Least privilege | Split further for expensive actions |
| Unknown tool | deny | Fail-closed | Never change |
| Rate limits | per tool, per principal | Blast radius | Tighten on anything irreversible |
| Audience validation | required | Cross-service replay | Never disable |
| `application_type` | native for desktop/CLI | Localhost redirects | Set correctly or flows break |
| Client registration | CIMD | Spec-current | DCR is deprecated — migrate |

## 8. Failure modes

| Symptom | Root cause | Detection | Mitigation |
|---|---|---|---|
| **Injected content triggers a cross-tenant read** | Scope taken from a tool argument | Audit: principal vs data accessed | Remove identity arguments entirely; derive from token |
| Token from service A works on service B | Audience not validated | Cross-service replay test | Validate `aud` on every request |
| Mix-up attack succeeds | `iss` not validated before code redemption | Code review of the client flow | RFC 9207 validation, client-side |
| Desktop client cannot complete OAuth | `application_type` unset; localhost redirect refused | Failed flows on desktop | Declare `application_type: native` |
| Clients cannot register | Relying on deprecated DCR | Registration failures | Migrate to CIMD |
| One agent loop exhausts the org quota | No per-principal rate limit | Calls per principal per hour | Rate limits per tool, per principal |
| Cannot attribute an action | Audit logs lack the principal | Incident review | Log principal, tenant, tool, args, outcome |
| Over-broad consent granted | Coarse scopes | Scope usage vs granted scopes | Split scopes by action and resource |
| Leaked token stays valid for a day | Long lifetime, no revocation | Time from report to invalidation | Short lifetimes + a revocation check |

## 9. Anti-patterns

- **`tenant_id` as a tool argument.** The defining MCP security mistake. Everything the model emits is untrusted.
- **Skipping audience validation.** Any token from the same issuer then works on your server.
- **Skipping `iss` validation before redeeming a code.** Exactly the attack RFC 9207 exists to stop.
- **A single "full access" scope.** Then every compromise is total.
- **Trusting `_meta` client identity for authorization.** It is informational; the token is authoritative.
- **Building your own OAuth server.** Use a real IdP. This is not the place for original work.
- **Static long-lived API keys shared across users.** No attribution, no revocation, no least privilege.
- **Rate limiting inside the agent loop.** The agent is what you are limiting; enforce server-side.

## 10. Metrics and SLOs

| Metric | Definition | Target | Alert at |
|---|---|---|---|
| Cross-tenant access | Requests serving data outside the principal's tenant | 0 | ≥ 1 (incident) |
| Auth failure rate | 401/403 / total | < 2% | > 10% |
| Token validation latency | p95 | < 20 ms | > 100 ms |
| Scope-denied rate | 403 from missing scopes | < 1% | > 5% (over-tight or misconfigured) |
| Rate-limit hits | Per principal per day | < 1% of principals | > 10% |
| Audit completeness | Calls with a principal recorded | 100% | < 100% |
| Token lifetime p95 | Issued lifetime | ≤ 1 h | > 24 h |

## 11. Scaling path

| Stage | Trigger to move up | What changes |
|---|---|---|
| v0 | — | stdio, no auth; process boundary is the boundary |
| v1 | Remote, internal, single team | Bearer token from a secret store, audience validated |
| v2 | Multiple users | OAuth 2.1 + PKCE, per-user tokens, token-derived scoping |
| v3 | Multiple orgs | Per-tenant isolation, scope granularity, per-principal rate limits |
| v4 | Third-party clients | CIMD, published protected-resource metadata, consent screens |
| v5 | Regulated | Short-lived tokens, revocation, immutable audit log, retention policy |

## 12. Build checklist

- [ ] No tool accepts `tenant_id`, `user_id`, or any identity argument.
- [ ] Scope is derived from token claims on every request.
- [ ] Token signature, **audience**, expiry, and scopes are all validated.
- [ ] The client validates `iss` (RFC 9207) before redeeming an authorization code.
- [ ] PKCE is used on every flow.
- [ ] Client identity uses CIMD; DCR is not relied on.
- [ ] `application_type` is declared for desktop/CLI clients.
- [ ] Protected-resource metadata is published at the well-known path.
- [ ] Unknown tools fail closed.
- [ ] Per-principal, per-tool rate limits exist for anything irreversible.
- [ ] Every call is audited with principal, tenant, tool, args, and outcome.
- [ ] A two-tenant isolation test runs in CI.
- [ ] Token lifetimes are short and revocation is possible.
